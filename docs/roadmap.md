# 学习总路线

## 场景与边界

读者具备 Python、文件 I/O、HTTP 和基础 SQL 知识。目标是实现一个能查代码、手册和库存数据的技术知识助手，并解释工具选择、证据质量、失败行为及成本。

采用一个小型 Python 样例仓库、几份带附录的产品手册、一个本地库存数据库。初期只支持可信本地单用户实验；不接企业真实数据。权限专题完成前不开放多用户服务。

核心概念是问题、来源版本、证据范围、候选排名与工具结果。所有阶段都必须保持：引用可追溯、无证据不编造、失败不伪装无结果、数据与指令分离。多租户阶段进一步要求未授权内容不能进入检索输出或模型上下文。

用户已确定的方向：一个独立系列，按专题及 v0-vn 组织。规划采用的假设：中文讲解、Python + uv、可本地重放的小型样例；具体模型和检索后端尚未选择。

## 依赖顺序

```text
01 评测 -> 02 代码检索
        -> 03 文档证据 -> 04 混合检索 -> 05 文档导航
        -> 06 实时查询
02 + 04 + 05 + 06 -> 07 Agent 循环
02 + 03 + 04 -> 08 权限 -> 09 索引运行（另需 04）
```

先完成 01 v0-v2，再做 03 和 04；代码任务可走 02 分支。07 的多轮查询应与单次检索基线比较，不能假定 Agent 更优。08 的完整安全实验独立编排，但基本路径限制与查询约束从第一个工具开始执行。

## 共同外部契约

初始标注使用 question_id、question、answerable 和 gold_evidence。证据包含 source_id、source_version 和可核验的范围；不同媒体的范围结构在 03 中明确，不能用不稳定块编号冒充原文位置。

检索输入为问题和有界结果数量；输出为排序证据及来源，不把不同检索器的原始分数当作同一尺度。身份来自可信执行上下文，不能取自模型自由填写的 tenant_id。

## 验收原则

质量按精确查询、语义改写、跨章节、实时数据、无答案分别报告。检索质量与回答支持度分别测量，人工标注是初始依据，LLM-as-judge 只能作经过校准的辅助。性能实验必须记录数据规模、模型、硬件、缓存与负载；不将小规模结果推广为生产容量保证。
