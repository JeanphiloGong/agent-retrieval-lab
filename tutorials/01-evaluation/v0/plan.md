## 首篇可执行写作任务

### 任务 1：建立读者场景与人工基准

读者是能编写 Python 的开发者，希望判断一个技术助手是否查到了正确证据。将问题压缩成两份自建文本、三道题，不需要模型、向量数据库或通用数据框架。

计划创建 `fixtures/evaluation/sources/errors-v1.txt` 和 `policy-v1.txt`。第一份说明 E104 是连接超时，第二份说明退款期限为七天。问题分别是 E104 的含义、换一种措辞询问退款期限、以及材料中没有的国际配送费用。

- 文档目标：`tutorial.md` 的场景与输入部分。
- 代码角色：数据 checkpoint；先写原文，再标注证据，不先设计类。
- 验收：前两题各有确切证据；第三题明确无答案，不虚构原文。
- 验证：逐条人工对照原文；将语义改写与精确词项问题分别归类。
- 前置：无；范围：S；checkpoint commit：no。

### 任务 2：把人工证据变成可检查的记录

原始基线是文本和手工笔记。压力样例是一条看似正确、实际指向错误行号的引用；只检查答案措辞无法发现这个问题。新增要求是标注必须指向可核验的原文。

创建 `fixtures/evaluation/questions.json`：每题包含 question_id、question、answerable 和 gold_evidence。每条证据包含 source_id、source_version、start_line、end_line 和 quote。使用 UTF-8 文本、从 1 开始且两端包含的行号；source_id 通过固定来源清单解析，不能直接作为任意文件路径。

- 文档目标：`tutorial.md` 的标注契约部分。
- 代码角色：checkpoint；目标为问题 JSON 与来源清单。
- 验收：问题 ID 唯一；answerable 为 false 时证据为空；为 true 时至少有一条证据；quote 与指定行范围内容相等。
- 验证：手工展示一次 question_id -> source_id/version -> 行范围 -> quote 的检查轨迹。
- 前置：任务 1；范围：S；checkpoint commit：no。
- 冻结：可人工验证的记录；仍无法自动发现坏标注，下一步增加检查程序。

### 任务 3：拒绝坏标注

已有合法记录；将其中一条 end_line 改到文件末尾之外，或复制 question_id，暴露手工复查容易漏错的缺口。只增加标注校验，不实现检索或答案生成。

实现 `labs/evaluation/validate.py`，接收标注文件与来源清单路径，校验通过返回退出码 0，失败以非零码报告问题 ID 和违反的规则。若需要 helper，只引入读取来源和验证记录两类函数：返回解析数据或验证错误，不修改输入文件。

- 文档目标：`tutorial.md` 的实现与失败实验部分。
- 代码角色：checkpoint；完整解释校验文件，依赖仅 Python 标准库。
- 验收：正常数据通过；重复 ID、错误字段类型、缺失来源、越界范围、引用不一致和不符合 answerable 约束的记录均拒绝。
- 验证：`tests/evaluation/test_validate.py` 使用标准库 unittest，在临时目录运行有效与无效样例；缺失文件和无效 JSON 不能变成成功。
- 前置：任务 2；范围：M；checkpoint commit：no。
- 冻结：可自动检查的标注集；尚无检索排名或检索指标。

### 任务 4：组装与重放完整 v0

在正文末尾给出全部数据与校验代码的对应文件清单、完整 checkpoint 和从仓库根目录运行的命令，不新增前文未解释的逻辑。

- 文档目标：`tutorial.md` 的完整检查点与边界部分。
- 代码角色：checkpoint；汇总 fixtures、validate.py 和 test_validate.py。
- 验收：新环境可通过 `uv run python -m unittest discover -s tests/evaluation` 重放；错误样例的实际退出码与教程相符；校验前后原文不变。
- 验证：在干净临时副本执行教程的所有命令，记录真实输出；当前规划没有执行这些未来命令。
- 前置：任务 3；范围：S；checkpoint commit：no，待用户要求保存通过复验的正文与代码时再提交。
